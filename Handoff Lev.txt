# 1. Роль Lev

Lev отвечает за **всю основную систему ПромВизора**:

* Video Source;
* OpenCV;
* YOLO;
* Person Detection;
* Motion Detection;
* ROI;
* Event Engine;
* определение простоя;
* расчёт времени простоя;
* расчёт ущерба;
* SQLite;
* FastAPI;
* API;
* Web Dashboard;
* frontend;
* интеграцию всех компонентов;
* DEMO-режим;
* интеграцию Telegram с backend.

Gasun отвечает **только за Telegram-бота**.

---

# 2. Главная архитектура

Основной pipeline:

```text
VIDEO
  ↓
OpenCV
  ↓
YOLO / COMPUTER VISION
  ↓
PERSON + MOTION
  ↓
ROI
  ↓
EVENT ENGINE
  ↓
DOWNTIME
  ↓
LOSS CALCULATION
  ↓
SQLite
  ↓
FastAPI
  ↓
┌───────────────┬────────────────┐
│ Web Dashboard │ Telegram Bot   │
│     LEV       │     GASUN      │
└───────────────┴────────────────┘
```

Главная цель Alpha:

**показать полный путь от видеопотока до обнаруженного простоя, расчёта ущерба, сохранения события и отображения результата.**

---

# 3. Что должен уметь MVP

Система должна получать видеопоток из:

1. DEMO video;
2. WEBCAM;
3. RTSP.

После этого система должна:

* определить человека;
* определить движение линии;
* учитывать ROI;
* определить состояние линии;
* определить простой;
* запустить таймер;
* рассчитать условный ущерб;
* сохранить событие;
* отдать данные через API;
* показать данные на Dashboard;
* передать событие Telegram-боту.

# 4. Video Source

Необходимо иметь единый интерфейс для источника видео.

Источники:

```text
DEMO
WEBCAM
RTSP
```

AI-модуль не должен зависеть от конкретного источника.

Условно:

```text
VideoSource
    ↓
get_frame()
    ↓
frame
    ↓
Vision
```

Это позволит использовать один и тот же AI pipeline для:

* демонстрационного видео;
* веб-камеры;
* реальной RTSP-камеры.

# 5. DEMO MODE

DEMO используется для демонстрации работы системы без реальной производственной камеры.

Видео должно быть явно обозначено:

> **DEMO MODE — демонстрационный видеопоток, имитирующий производственную камеру.**

AI-generated видео нельзя выдавать за реальную запись предприятия.

## 6.4 Downtime

Главный сценарий:

```text
MOVING + PERSON PRESENT
        ↓
LINE STOPPED
        ↓
PERSON LEAVES ROI
        ↓
STOPPED + PERSON ABSENT
        ↓
N секунд
        ↓
DOWNTIME
```

После этого:

```text
DOWNTIME
↓
TIMER
↓
LOSS
↓
DATABASE
↓
DASHBOARD
↓
TELEGRAM
```

# 7. Person Detection

Используется YOLO.

Главный результат:

```python
person_present: bool
```

В будущем при необходимости можно добавить:

* bounding boxes;
* confidence;
* YOLO Pose.

Но для Alpha достаточно:

```text
PERSON PRESENT
PERSON ABSENT
```

Важно использовать формулировку:

> **Рабочий не обнаружен в контролируемой зоне камеры.**

Не использовать:

> Рабочий отсутствует на предприятии.

Система видит только то, что попадает в камеру.

---

# 8. ROI

ROI — контролируемая область камеры.

Она используется для определения:

> находится ли человек в рабочей зоне.

Например:

```text
┌─────────────────────────────┐
│                             │
│       CONVEYOR              │
│  ┌───────────────────────┐  │
│  │       ROI             │  │
│  │                       │  │
│  │      👤 WORKER        │  │
│  │                       │  │
│  └───────────────────────┘  │
│                             │
└─────────────────────────────┘
```

YOLO обнаруживает человека, после чего система проверяет, попадает ли его положение в ROI.

---

# 9. Motion Detection

Для определения движения конвейера используется:

* OpenCV;
* анализ изменения изображения;
* ROI;
* при необходимости Optical Flow.

Результат:

```text
MOVING
STOPPED
UNKNOWN
```

Нельзя определять остановку по одному кадру.

Нужно использовать временную устойчивость:

```text
несколько последовательных кадров
        ↓
подтверждение STOPPED
```

Это снижает количество ложных срабатываний.

# 10. Event Engine

Основная логика:

```text
MOVING + PERSON PRESENT
→ NORMAL
```

```text
MOVING + PERSON ABSENT
→ NORMAL / NO DOWNTIME
```

```text
STOPPED + PERSON PRESENT
→ POSSIBLE MAINTENANCE
```

```text
STOPPED + PERSON ABSENT
→ POSSIBLE DOWNTIME
```

Если:

```text
STOPPED + PERSON ABSENT
```

продолжается больше заданного порога:

```text
N секунд
```

создаётся:

```text
DOWNTIME
```

# 13. Loss Calculation

Формула:

```text
loss = downtime_minutes × cost_per_minute
```

Пример:

```text
100 минут × 750 ₽
=
75 000 ₽
```

Расчёт выполняется **backend'ом Lev**.

Dashboard и Telegram только отображают готовое значение.

# 16. FastAPI

FastAPI полностью находится на стороне Lev.

Структура:

```text
app/api/
├── routes.py       # endpoints
├── schemas.py      # схемы ответов
```

`main.py` и `demo_data.py` добавлены сверх исходного списка: без точки
входа сервер нечем запустить, а без демо-данных интерфейс нечего
показать до Этапа 9 (DEMO-ролики ещё не получены).

API должен предоставлять данные для:

* Dashboard;
* Telegram Bot;
* потенциальных внешних интеграций.

Пример логики:

```text
GET /api/status
```

→ текущее состояние системы.

```text
GET /api/events
```

→ история событий.

```text
GET /api/events/{id}
```

→ конкретное событие.

Названия endpoints можно изменить в процессе разработки, но контракт должен оставаться понятным.

## Этап 6 — API (реализовано)

### Запуск

```bash
.venv/bin/python -m app.api.main
```

Документация: `http://127.0.0.1:8000/docs`

Через CLI: `.venv/bin/uvicorn app.api.main:app --port 8000`.
CLI не читает `API_PORT` из настроек — порт указывается аргументом.

### Endpoints

| Метод | Путь | Назначение |
|-------|------|------------|
| GET | `/api/status` | текущее состояние (`SystemStatus`) |
| GET | `/api/status/history` | снимки состояния, свежие сверху |
| GET | `/api/events` | история простоя, с фильтрами и пагинацией |
| GET | `/api/events/{id}` | одно событие, 404 если нет |
| GET | `/api/statistics` | итоги за период (`Statistics`) |
| GET | `/api/statistics/by-camera` | итоги по камерам |
| GET | `/api/cameras` | зарегистрированные камеры |
| GET | `/api/config` | стоимость минуты и настройки |
| GET | `/api/health` | живость сервиса и базы |
| POST | `/api/demo/seed` | наполнить базу демо-данными |

Имена `/api/status`, `/api/events`, `/api/events/{id}` — как в
разделе 16, чтобы Gasun не пришлось ничего угадывать. Поля ответов
повторяют контракт `app/core/types.py` один в один.

### Что важно знать

* **Ущерб не пересчитывается в API.** Значение приходит из базы
  таким, как его посчитал backend (раздел 14).
* **Пустая база — не ошибка.** `/api/status` отдаёт `UNKNOWN` с
  нулями, чтобы клиент показал «нет данных», а не упал.
* **API только читает.** Запись идёт из процесса обработки видео
  прямо в базу, так API нельзя испортить внешним запросом.
* **`total` в `/api/events`** — сколько событий подходит под фильтр
  без учёта `limit`, чтобы показать «показано 20 из 143».
* **Соединение с базой — на поток.** FastAPI выполняет обычные
  endpoints в пуле потоков, а `sqlite3` требует использовать
  соединение только в том потоке, где оно создано. Одно общее
  соединение давало бы 500 на каждом запросе. Подробнее в Этапе 5.
* **Демо-данные не подгоняются под «красиво».** Длительности
  случайны, но ущерб считается той же `calculate_loss()`. Простоя
  выходят 4–40 минут, суммарно около 2% времени — на остановку
  завода это не похоже.
* **Демо-данные по явному запросу** (`POST /api/demo/seed`).
  Молча наполнять базу нельзя: Dashboard показал бы цифры, которых
  на заводе нет. По умолчанию демо не затирает реальные данные,
  есть флаг `replace=true`.
* **События из будущего не создаются** — интервалы, до которых линия
  ещё не дошла, отбрасываются, иначе они попали бы в статистику за
  сегодня как уже случившиеся.

# 17. Web Dashboard

Dashboard теперь полностью делает Lev.

Структура (уточнено 10.10.2026 — фактическое имя каталога `web/`,
разбивка на модули вместо одного файла):

```text
web/
├── index.html
├── css/
│   └── styles.css          # темы, карточки, таймлайн, адаптив
└── js/
    ├── data.js             # мок-слой по контракту app/core/types.py
    ├── components.js       # иконки, тосты, делегирование событий
```

Модульное разделение выбрано вместо монолитного `app.js`, потому что
разделов шесть и каждый sizeable; при объединении в один файл любая
правка затрагивала бы весь интерфейс.

### ⚠️ Расхождение в терминах: WORKING или MOVING

`CONTRACT.md` и `app/core/types.py` требуют `WORKING`,
а раздел 9 этого документа — `MOVING`. Это **одно и то же состояние**
под разными именами.

Реализовано по контракту (`WORKING`), потому что `CONTRACT.md` прямо
запрещает менять состав полей без согласования Lev и Gasun.

**Решение принято 10.10.2026: остаётся `WORKING`.**

`WORKING` — это значение из `app/core/types.py` (`LineStatus`),
оно же зафиксировано в `CONTRACT.md`. Если у Gasun возникнут
проблемы с чтением `line_status` — меняется его код, а не контракт.
Менять `WORKING` на `MOVING` в системе не планируется.

### Что защищено от ложных срабатываний

* решение принимается по **нескольким последовательным кадрам**
  (прогрев `motion_min_samples`), а не по одному
* **гистерезис**: после STOPPED нужно больше движения, чтобы вернуться
  в WORKING
* **отбраковка кадров со сменой освещения**: заслон объектива или
  включение света резко меняют весь кадр и выглядят как движение.
  Такие кадры не считаются движением, состояние сохраняется
* **сравнение соседних кадров**, а не с одним «эталонным»: иначе
  линия, остановившаяся навсегда, вечно отличалась бы от первого
  кадра и читалась как работающая

### Логика (раздел 10)

```text
MOVING + PERSON PRESENT  → NORMAL, простоя нет
MOVING + PERSON ABSENT   → NORMAL, простоя нет (рабочий просто отошёл)
STOPPED + PERSON PRESENT → обслуживание, простоя нет
STOPPED + PERSON ABSENT  → простой, если держится дольше порога N
```

### Защита от ложных событий

* **`UNKNOWN` — не значит `STOPPED`.** При неопределённом состоянии
  простой не подтверждается, но и **не закрывается**: нет данных,
  значит нельзя утверждать, что линия заработала
* **порог подтверждения** — условие короче `downtime_threshold_seconds`
  отменяется молча, без событий
* **подтверждение восстановления** (`downtime_resume_confirm_seconds`) —
  микропаузы конвейера не плодят пары STARTED/FINISHED
* **монотонность времени** — попытка откатить время приводит к
  ошибке, а не к тихой порче расчёта

### Важная деталь: с какого момента считается простой

Простой считается **с момента, когда условие впервые выполнилось**,
а не с момента подтверждения. Порог — это задержка подтверждения,
а не часть простоя: линия стоит с `pending_since`, и потери
производства тоже с него.

### События и контракт

Внутренние события (`DowntimeStarted` / `DowntimeFinished`) отделены
от контрактного `DowntimeEvent`: таймер не знает про формат `HH:MM`
и стоимость минуты. Преобразование — `to_contract()`, один раз
на границе с БД/API.

### Решения, которые стоит знать

* **Без ORM.** Для трёх таблиц и Alpha-версии `sqlalchemy` дала бы
  лишнюю зависимость и слой абстракции поверх простых запросов.
* **Автокоммит (`isolation_level=None`).** По умолчанию Python-оверлей
  sqlite3 сам открывает транзакцию перед `INSERT` и **не коммитит** —
  данные молча терялись при закрытии соединения. Обнаружено тестом
  на переподключение.
* **`PRAGMA foreign_keys = ON`.** В SQLite внешние ключи выключены
  по умолчанию: без этой строки каскадное удаление не работало бы
  и событие можно было бы записать для несуществующей камеры.
* **Время записи — в UTC.** Локальное время процесса меняется
  (часы, переезд, другой часовой пояс), а история простоя — нет.
  В самом событии `start_time` / `end_time` остаются «HH:MM».
* **WAL-режим.** Статусы пишутся постоянно и читаются параллельно:
  WAL не блокирует читателя писателем.
* **`limit` санируется.** Отрицательный `LIMIT` в SQLite — это не
  «все строки», а «без нижней границы», что здесь опасно.

просто не было бы.

### Почему так устроено

* **Разделы не переписаны под async.** `sections.js` перерисовывается
  синхронно, поэтому `data.load()` асинхронно наполняет кэш, а
  чтение остаётся синхронным. Правки отрисовки не потребовались —
  изменился только источник данных.
* **Ущерб не пересчитывается.** В `data.js` нет формулы: значение
  `estimated_loss` используется как есть. Проверено тестом — при смене
  стоимости минуты суммы на экране не меняются.
* **Без сервера показывается демо-режим**, и это написано прямо:
  «Нет связи с сервером — показаны демонстрационные значения».
  Молча подсовывать выдумку нельзя: на Dashboard смотрел бы человек,
  решивший бы, что линия стоит.
* **Обрыв связи не стирает данные.** Последние показания остаются на
  экране с пометкой обрыва — индикатор в сайдбаре становится янтарным.
* **Сотрудники остаются демонстрационными.** В контракте их нет и
  backend их не ведёт. Раздел помечен предупреждением: выдумывать API
  под него — значит выдумывать и данные.

### Три линии, а не «сколько знает сервер»

Наряд линий — конфигурация цеха (три линии), а не ответ `/api/cameras`.
Сперва линии вычислялись из списка камер, и при одной зарегистрированной
камере весь интерфейс сжимался до одного столбца: ломались таймлайн,
сводка и отчёты. Теперь линии задаются настройкой, а камера
показывается для каждой: если сервер о камере не знает, она честно
помечена «Офлайн». Иначе при переключении на «Линию 2» заголовок
продолжал бы называть «Камера №1», то есть показывать чужую камеру.

Панель текущего состояния стоит на вкладке «Камеры», а не «Линии»:
на «Линиях» она читалась как лишняя камера. Свой заголовок не
дублирует имя камеры — оно уже есть в карточке ниже.

### Найдено и исправлено при подключении

* **`load()` не ходил на сервер повторно.** Если день уже в кэше,
  запрос не уходил — «текущее состояние» замирало навсегда. Добавлен
  `reload()` с обходом кэша; автообновление вызывает его.
* **Смешение UTC и местного времени.** У открытого простоя длительность
  считалась как «местное сейчас минус время события», а время события
  приходит в UTC. Выходили простои по 6–10 часов вместо минут, и
  итоги в отчёте были завышены в разы. Теперь берётся реальное
  прошедшее время между меткой записи и «сейчас».
* **Открытый простой попадал в итоги.** Он не завершён и ущерба не
  имеет, но суммировался вместе с завершёнными. Теперь таймлайн его
  рисует (пунктирная рамка, «идёт»), а итоги считают только завершённые
  — так же, как `/api/statistics` на backend'е.
* **Частичный отказ молча показывал пустой экран** с подписью «данные
  с сервера». Теперь отсутствие любого обязательного ответа переводит
  интерфейс в демо-режим с внятной причиной.
* **Тост врал при обрыве:** «связь установлена» появлялось по
  наличию данных, а не по факту связи.

### Про события без даты

В контракте `DowntimeEvent` нет даты — только «ЧЧ:ММ». Интерфейсу
она нужна: без неё не собрать ни таймлайн за сутки, ни отчёт за
месяц. Поэтому API отдаёт в событии дополнительное поле `created_at`
(метка записи в базе, ISO 8601 UTC). **Контракт от этого не меняется** —
это поле есть только в ответе API.

Демо — это снимок, сделанный в момент `POST /api/demo/seed`. Открытый

# Конвейер видео, режим камеры и трек человека (10.10.2026)

Реализовано по требованию, заданному пользователем 10.10.2026:
**режим камеры переключается в настройках**, а в окне камер видно
**живое видео с зелёной рамкой вокруг человека, его номером и
пройденным путём**.

## Что работает

| Требование | Как сделано |
|---|---|
| Выбор режима в настройках | `demo` / `synthetic` / `webcam` / `rtsp` |
| Демо-режим — ролики сценариев | `app/video/demo.py`; пока роликов нет — синтетика |
| Веб-камера — наглядный показ | живой MJPEG с разметкой |
| Человек есть — сообщения нет | рамка зелёная, `WORKING`, простоя нет |
| Человек ушёл → 5 секунд → в отчёт | `downtime_threshold_webcam_seconds = 5` |
| Рамка, номер и путь | зелёный прямоугольник + «Рабочий N» + линия пути |
| Выбор камеры в настройках | список устройств с backend'а |
| Сетевая камера — «нет сигнала» | режим есть, но включать нечего |

## Структура

```text
app/pipeline/
├── runner.py      цикл: кадр → детекция → события → база → разметка
├── tracker.py     сопоставление людей между кадрами, история пути
├── overlay.py     отрисовка рамки, номера, пути, ROI
└── synthetic.py   сцена без DEMO-роликов (витрина механики)

app/api/
├── stream.py      MJPEG-поток, режим камеры, список веб-камер
└── runtime.py     один конвейер на процесс, перезапуск при смене режима

app/core/camera_mode.py   режим камеры: чтение и сохранение выбора
```

## Решения, о которых стоит знать

* **Простой — это отсутствие рабочего, а не остановка конвейера.**
  По ТЗ: «человек есть — сообщения нет, вышел — через 5 секунд в
  отчёт». Поэтому в режимах веб-камеры и синтетики отсутствие
  человека трактуется как `STOPPED`. Иначе простой не наступил бы
  никогда: конвейер в кадре движется.
* **5 секунд — порог именно веб-камеры** (`downtime_threshold_webcam_seconds`).
  В демо-режиме порог другой: ролик длится секунды, и пять секунд
  ожидания там означали бы, что событие не наступит никогда.
* **Синтетика сообщает свой бокс вместо YOLO.** YOLO обучена на
  фотографиях людей; силуэт из прямоугольников она не признаёт —
  проверено, уверенность оставалась нулевой. Для синтетики известный
  бокс — честный выход: это витрина механики, а не измерение.
  Настоящая детекция проверяется на веб-камере и DEMO-роликах.
* **Трекер — свой, около сотни строк.** ultralytics умеет трекить
  сам, но там трекер встроен в их пайплайн и не переиспользуется
  отдельно от нашей детекции.
* **Конвейер живёт в своём потоке**, а не в запросе: обработка идёт
  постоянно и не должна ждать HTTP-запроса. API только читает.
* **Смена режима сохраняется в `camera_mode.json`**, а не в `.env`:
  `.env` читается только при старте процесса, а переключать режим
  нужно на работающей системе.
* **Частота кадров ограничена** (`MAX_PIPELINE_FPS = 15`). Без этого
  синтетика прокручивалась за секунды вместо минут, и длительность
  простоя в отчёте была бы неверной.

## Найдено и исправлено при разработке

* **Конвейер писал в незарегистрированную камеру.** У событий и
  статусов внешний ключ, и без `ensure_camera` каждая запись падала с
  `FOREIGN KEY constraint failed` — тихо, конвейер при этом жил, а
  база оставалась пустой.
* **`Roi.to_pixels` возвращает (x, y, w, h), а не углы
  прямоугольника.** Использованный как углы, он давал зону вдвое
  меньше нужного, и присутствие человека не определялось никогда:
  простоя в отчёте не было никогда. Используется готовый
  `Roi.contains_box` — он считает перекрытие, а не центр.
* **Новые треки тут же выбрасывались.** Счётчик пропусков
  увеличивался после создания, и только что появившийся человек
  получал `misses=1` и не отображался.
* **OpenCV не принимает дробные координаты** — путь не рисовался.
* **Сообщение о недоступности источника перетиралось** общим текстом
  «не удалось открыть», и оператор не видел причину.
* **`.is-hidden` в CSS был привязан к вкладкам** — поле выбора камеры
  оставалось видимым во всех режимах.
