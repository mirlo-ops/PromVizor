# 1. Роль Lev

Lev отвечает за **всю основную систему ПромВизора**:

* Video Source;
* OpenCV;
* YOLO;
* Person Detection;
* Motion Detection;
* ROI;
* Event Engine;
* определение простоя;
* расчёт времени простоя;
* расчёт ущерба;
* SQLite;
* FastAPI;
* API;
* Web Dashboard;
* frontend;
* интеграцию всех компонентов;
* DEMO-режим;
* интеграцию Telegram с backend.

Gasun отвечает **только за Telegram-бота**.

---

# 2. Главная архитектура

Основной pipeline:

```text
VIDEO
  ↓
OpenCV
  ↓
YOLO / COMPUTER VISION
  ↓
PERSON + MOTION
  ↓
ROI
  ↓
EVENT ENGINE
  ↓
DOWNTIME
  ↓
LOSS CALCULATION
  ↓
SQLite
  ↓
FastAPI
  ↓
┌───────────────┬────────────────┐
│ Web Dashboard │ Telegram Bot   │
│     LEV       │     GASUN      │
└───────────────┴────────────────┘
```

Главная цель Alpha:

**показать полный путь от видеопотока до обнаруженного простоя, расчёта ущерба, сохранения события и отображения результата.**

---

# 3. Что должен уметь MVP

Система должна получать видеопоток из:

1. DEMO video;
2. WEBCAM;
3. RTSP.

После этого система должна:

* определить человека;
* определить движение линии;
* учитывать ROI;
* определить состояние линии;
* определить простой;
* запустить таймер;
* рассчитать условный ущерб;
* сохранить событие;
* отдать данные через API;
* показать данные на Dashboard;
* передать событие Telegram-боту.

# 4. Video Source

Необходимо иметь единый интерфейс для источника видео.

Источники:

```text
DEMO
WEBCAM
RTSP
```

AI-модуль не должен зависеть от конкретного источника.

Условно:

```text
VideoSource
    ↓
get_frame()
    ↓
frame
    ↓
Vision
```

Это позволит использовать один и тот же AI pipeline для:

* демонстрационного видео;
* веб-камеры;
* реальной RTSP-камеры.

---

# 5. DEMO MODE

DEMO используется для демонстрации работы системы без реальной производственной камеры.

Видео должно быть явно обозначено:

> **DEMO MODE — демонстрационный видеопоток, имитирующий производственную камеру.**

AI-generated видео нельзя выдавать за реальную запись предприятия.

# 6. Демо-сценарии

Минимально нужны 4 сценария.

## 6.1 Normal

```text
MOVING
+
PERSON PRESENT
```

Ожидаемое состояние:

```text
NORMAL
```

---

## 6.2 Line stopped

```text
MOVING
+
PERSON PRESENT

↓

STOPPED
+
PERSON PRESENT
```

Это ещё не обязательно простой.

Это может быть:

* обслуживание;
* наладка;
* корректировка оборудования.

---

## 6.3 Person absent

```text
MOVING
+
PERSON PRESENT

↓

MOVING
+
PERSON ABSENT
```

Отсутствие человека само по себе **не должно создавать простой**.

---

## 6.4 Downtime

Главный сценарий:

```text
MOVING + PERSON PRESENT
        ↓
LINE STOPPED
        ↓
PERSON LEAVES ROI
        ↓
STOPPED + PERSON ABSENT
        ↓
N секунд
        ↓
DOWNTIME
```

После этого:

```text
DOWNTIME
↓
TIMER
↓
LOSS
↓
DATABASE
↓
DASHBOARD
↓
TELEGRAM
```

# 7. Person Detection

Используется YOLO.

Главный результат:

```python
person_present: bool
```

В будущем при необходимости можно добавить:

* bounding boxes;
* confidence;
* YOLO Pose.

Но для Alpha достаточно:

```text
PERSON PRESENT
PERSON ABSENT
```

Важно использовать формулировку:

> **Рабочий не обнаружен в контролируемой зоне камеры.**

Не использовать:

> Рабочий отсутствует на предприятии.

Система видит только то, что попадает в камеру.

---

# 8. ROI

ROI — контролируемая область камеры.

Она используется для определения:

> находится ли человек в рабочей зоне.

Например:

```text
┌─────────────────────────────┐
│                             │
│       CONVEYOR              │
│  ┌───────────────────────┐  │
│  │       ROI             │  │
│  │                       │  │
│  │      👤 WORKER        │  │
│  │                       │  │
│  └───────────────────────┘  │
│                             │
└─────────────────────────────┘
```

YOLO обнаруживает человека, после чего система проверяет, попадает ли его положение в ROI.

---

# 9. Motion Detection

Для определения движения конвейера используется:

* OpenCV;
* анализ изменения изображения;
* ROI;
* при необходимости Optical Flow.

Результат:

```text
MOVING
STOPPED
UNKNOWN
```

Нельзя определять остановку по одному кадру.

Нужно использовать временную устойчивость:

```text
несколько последовательных кадров
        ↓
подтверждение STOPPED
```

Это снижает количество ложных срабатываний.

---

# 10. Event Engine

Основная логика:

```text
MOVING + PERSON PRESENT
→ NORMAL
```

```text
MOVING + PERSON ABSENT
→ NORMAL / NO DOWNTIME
```

```text
STOPPED + PERSON PRESENT
→ POSSIBLE MAINTENANCE
```

```text
STOPPED + PERSON ABSENT
→ POSSIBLE DOWNTIME
```

Если:

```text
STOPPED + PERSON ABSENT
```

продолжается больше заданного порога:

```text
N секунд
```

создаётся:

```text
DOWNTIME
```

---

# 11. Downtime

Downtime должен иметь как минимум состояния:

```text
IDLE
DOWNTIME
```

При начале простоя:

```text
downtime_started_at
```

При восстановлении движения:

```text
downtime_ended_at
```

Продолжительность:

```text
downtime_seconds
```

# 12. Ускоренное DEMO-время

Для презентации желательно использовать ускоренное время.

Например:

```text

00:10

рабочий ушёл

00:15
↓

00:30
↓

```

И показать условный ущерб:

```text
100 × 750 ₽
=
75 000 ₽
```

# 13. Loss Calculation

Формула:

```text
loss = downtime_minutes × cost_per_minute
```

Пример:

```text
100 минут × 750 ₽
=
75 000 ₽
```

Расчёт выполняется **backend'ом Lev**.

Dashboard и Telegram только отображают готовое значение.

# 14. Общий SystemStatus

Файл:

```text
app/core/types.py
```

Контракт:

```python
from dataclasses import dataclass

@dataclass
class SystemStatus:
    camera_id: int
    line_status: str
    person_present: bool
    downtime_seconds: int
    estimated_loss: float
```

Пример:

```python
SystemStatus(
    camera_id=1,
    line_status="STOPPED",
    person_present=False,
    downtime_seconds=120,
    estimated_loss=1500
)
```

### Правило

**Lev отвечает за корректность данных.**

Другие компоненты не должны самостоятельно пересчитывать эти значения.

## Решение по расчёту ущерба (10.10.2026)

Handoff (раздел 14) запрещает интерфейсу пересчитывать `estimated_loss`.
Раньше фронтенд считал ущерб сам (`× 12.5` в двух местах, игнорируя
настройку `cost_per_minute`) — это было нарушением контракта.

Сейчас:

* формула вынесена в `app/core/types.py` → `calculate_loss()`
* в `web/js/data.js` ущерб приходит как **готовое значение**
  (`backendLoss()` — имитация ответа сервера)
* стоимость минуты задаётся из настроек через
  `data.setCostPerMinute()` — фронтенд получает цифру, а не считает её
* проверено: суммы на Dashboard совпадают с расчётом по формуле Lev

**При подключении реального API функция `backendLoss()` заменяется на
значение из ответа `/api/status` и `/api/events`.**

### ⚠️ Расхождение в терминах: WORKING или MOVING

`CONTRACT.md` и `app/core/types.py` требуют `WORKING`,
а раздел 9 этого документа — `MOVING`. Это **одно и то же состояние**
под разными именами.

Реализовано по контракту (`WORKING`), потому что `CONTRACT.md` прямо
запрещает менять состав полей без согласования Lev и Gasun.

**Нужно решение:** если Gasun уже читает `MOVING` из API — менять
нужно контракт, а не код. Пока не согласовано, код использует
`WORKING`, а `LineStatus` остаётся источником истины.

### Что защищено от ложных срабатываний

* решение принимается по **нескольким последовательным кадрам**
  (прогрев `motion_min_samples`), а не по одному
* **гистерезис**: после STOPPED нужно больше движения, чтобы вернуться
  в WORKING
* **отбраковка кадров со сменой освещения**: заслон объектива или
  включение света резко меняют весь кадр и выглядят как движение.
  Такие кадры не считаются движением, состояние сохраняется
* **сравнение соседних кадров**, а не с одним «эталонным»: иначе
  линия, остановившаяся навсегда, вечно отличалась бы от первого
  кадра и читалась как работающая
