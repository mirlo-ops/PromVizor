# ПромВизор — API для Telegram Bot

**Кому:** Gasun (разработчик Telegram Bot).
**Что нужно сделать:** бот должен забирать у backend'а состояние
системы и события простоя и отправлять сообщения.
**Что делать НЕ нужно:** считать ущерб, определять простой, разбирать
видео. Всё это уже сделано на стороне Lev.

Документ описывает API, который уже работает. Примеры ответов в нём
взяты из живого сервера, а не придуманы.

---

## 1. Главное правило

> **Ущерб приходит готовым. Считать его на стороне бота нельзя.**

В ответах есть поле `estimated_loss` — это готовая сумма в рублях.
Бот показывает её как есть.

Почему так: формулу считает только backend (`calculate_loss()` в
`app/core/types.py`). Если бот посчитает сам по своей копии правил,
суммы разойдутся с Dashboard и с отчётом, и при расхождении никто не
поймёт, где ошибка. Это требование зафиксировано в разделе 14 Handoff.

По той же причине боту не нужно знать про порог простоя, ROI, модель
детекции и прочие внутренние настройки. Всё это учтено на backend'е.

## 2. Как запустить

```bash
.venv/bin/python -m app.api.main
```

После запуска:

| Адрес | Что |
|---|---|
| `http://127.0.0.1:8000/api/status` | состояние прямо сейчас |
| `http://127.0.0.1:8000/docs` | документация с примерами (Swagger) |

переподключаться: пользователю не показывают «ошибка», когда сервис
просто перезапускается.

## 3. Текущее состояние

```text
GET /api/status
```

Ответ:

```json
{
  "camera_id": 1,
  "line_status": "WORKING",
  "person_present": true,
  "downtime_seconds": 0,
  "estimated_loss": 0.0
}
```

Поля:

| Поле | Значение | Что значит |
|---|---|---|
| `camera_id` | целое | номер камеры |
| `line_status` | `WORKING` / `STOPPED` / `UNKNOWN` | состояние линии |
| `person_present` | true / false | рабочий в контролируемой зоне |
| `downtime_seconds` | целое | идущий сейчас простой, секунды |
| `estimated_loss` | число | ущерб за идущий простой, ₽ |

Три состояния линии, а не два:

* `WORKING` — линия работает;
* `STOPPED` — линия стоит;
* `UNKNOWN` — состояние определить не удалось (например, нет данных
  с камеры). **Это не то же, что `STOPPED`**: при `UNKNOWN` бот не
  должен присылать сообщение о простое.

Пустая база (система только запустилась) тоже отдаёт `UNKNOWN` и
нули. Это нормальное состояние, а не ошибка.

## 4. События простоя

```text
GET /api/events?limit=50
```

Ответ (живой сервер):

```json
{
  "items": [
    {
      "camera_id": 1,
      "event": "DOWNTIME_STARTED",
      "start_time": "07:33",
      "end_time": "",
      "duration_seconds": 0,
      "estimated_loss": 0.0,
      "id": 1,
      "created_at": "2026-10-10T14:46:04+00:00"
    },
    {
      "camera_id": 1,
      "event": "DOWNTIME_FINISHED",
      "start_time": "07:33",
      "end_time": "07:34",
      "duration_seconds": 9,
      "estimated_loss": 112.5,
      "id": 2,
      "created_at": "2026-10-10T14:46:10+00:00"
    }
  ],
  "count": 2,
  "total": 2
}
```

### Поля события

| Поле | Что значит |
|---|---|
| `id` | номер строки в базе, **строго возрастает** |
| `event` | `DOWNTIME_STARTED` или `DOWNTIME_FINISHED` |
| `start_time` | когда начался простой, «ЧЧ:ММ» |
| `end_time` | когда закончился, «ЧЧ:ММ»; пусто у незакрытого |
| `duration_seconds` | длительность простоя, секунды |
| `estimated_loss` | **готовый** ущерб, ₽ |
| `created_at` | метка времени записи, ISO 8601 **в UTC** |
| `camera_id` | номер камеры |

Дополнительно у ответа: `count` — сколько событий в этой выдаче,
`total` — сколько всего в базе (для пагинации).

### События приходят парами

```text
DOWNTIME_STARTED  →  простой начался
DOWNTIME_FINISHED →  простой закончился, появились длительность и ущерб
```

**Отправлять сообщение боту имеет смысл по `DOWNTIME_FINISHED`**
только там, где он отправляет сообщение при начале простоя, берите
`DOWNTIME_STARTED`, но учтите: в нём `estimated_loss` всегда `0.0`,
потому что ущерб считается при завершении.

Формулировки (раздел 18 Handoff) важны. Система видит только то, что
попало в камеру, поэтому утверждать, что сотрудник «отсутствовал на
предприятии», нельзя:

```text
✅ Рабочий не обнаружен в контролируемой зоне камеры.
❌ Рабочий отсутствует на предприятии.
```

## 5. Как читать новые события без повторов

Ключ — поле `id`. Оно строго возрастает, поэтому бот запоминает
последнее прочитанное значение и просит только то, что появилось
позже.

### 5.1. Фильтры

```text
GET /api/events?limit=50                    последние 50 (новые сверху)
GET /api/events?event_type=DOWNTIME_FINISHED
GET /api/events?since=2026-10-01&until=2026-10-10
GET /api/events?camera_id=1
```

`limit` — от 1 до 1000. `since` / `until` — даты (включительно),
фильтруют по `created_at` в UTC.

### 5.2. Страница возвращается новыми сверху

`items[0]` — самое свежее событие, дальше к старым. Значит обрабатывать
их нужно **снизу вверх** (через `reversed()`), иначе уведомления
придут в обратном порядке.

Порядок зафиксирован тестом. Раньше он был противоположным тому, что
написано здесь, и код, написанный по этому тексту, обрабатывал
события задом наперёд.

### 5.3. Курсор

```python
last_id = 0                      # при первом запуске
# в памяти или в своём хранилище

# потом в каждом цикле:
data = get_json(f"{BASE}/api/events?limit=200")
for event in reversed(data["items"]):     # ← снизу вверх, от старых к новым
    if event["id"] <= last_id:
        continue
    handle(event)
    last_id = event["id"]
```

Два важных момента:

* `reversed()` — потому что события приходят новыми сверху, а
  обрабатывать их надо от старых к новым, иначе уведомления придут
  в обратном порядке.
* при первом запуске `last_id = 0` пришлёт **всё, что накопилось за
  время работы системы**. Обычно это нежелательно: бот не должен
  засыпать сообщениями за неделю. Поэтому при первом запуске
  разумнее сначала прочитать `total` из ответа и запомнить
  `last_id = total` — то есть пропустить историю:

```python
if last_id is None:                       # первый запуск
    # Берём id последнего события, а НЕ поле total: при фильтре
    # event_type total — это число ОТФИЛЬТРОВАННЫХ событий, оно
    # меньше максимального id, и курсор занизился бы — бот прислал бы
    # несколько старых событий. Поэтому спрашиваем без фильтра.
    first = get_json(f"{BASE}/api/events?limit=1")
    items = first.get("items") or []
    last_id = items[0]["id"] if items else 0
    # историю пропускаем, ждём новых событий
```

Ещё одна причина спрашивать без фильтра: `items` приходят **новыми
сверху**, поэтому `items[0]` — самое свежее событие во всей базе, а
не в отфильтрованной выборке.
```

### 5.4. Что делать с `DOWNTIME_STARTED`

Он приходит сразу после достижения порога. Решайте сами, присылать
сообщение о начале или только об итоге. Если нужен итог — отфильтруйте
`event_type=DOWNTIME_FINISHED` и обрабатывайте только его.

```text

  "total_downtime_seconds": 1368,

```text

}
```

`cost_per_minute` — **только для подписи** («за минуту — 750 ₽»).
Пересчитывать по нему `estimated_loss` нельзя.

## 7. О времени — прочитать внимательно

Два разных времени в одном событии, и перепутать их легко:

| Поле | Часовой пояс | Как использовать |
|---|---|---|
| `start_time`, `end_time` | **местное время машины** с backend'а | показать человеку в сообщении |
| `created_at` | **всегда UTC** | фильтровать, делить сутки, хранить |

Пример из живого ответа:

```json
"start_time": "07:33",
"created_at": "2026-10-10T14:46:10+00:00"
```

Разница 7 часов — это UTC+7 у машины с backend'ом, а не ошибка. Если
бот запущен на другой машине, его «сейчас» может отличаться от
местного времени завода. Считайте, что в сообщениях надо показывать
время завода (это `start_time`), а для своих расчётов и хранения
использовать `created_at` из UTC.

## 8. Коды ответа

| Код | Когда | Что делать |
|---|---|---|
| 200 | всё в порядке | обрабатывать |
| 404 | `/api/events/{id}` — события нет | обычно это «ещё не пришло» |
| 422 | неверный параметр (например, `event_type=ВЗРЫВ`) | проверить запрос, логировать |
| 503 | сервис ещё не готов | подождать и повторить |
| — | сервер не отвечает | повторять с паузой, сообщение пользователю не слать |

Пример текста ошибки:

```json
{"detail": "Неизвестный тип события: ВЗРЫВ. Допустимые: DOWNTIME_STARTED, DOWNTIME_FINISHED"}
```

## 9. Готовый пример

```python
"""Чтение простоя из «ПромВизора» и отправка в Telegram."""

import logging
import time

import requests

from telegram import Bot
from telegram.constants import ParseMode

BASE = "http://127.0.0.1:8000"
BOT = Bot(token="...")
CHAT_ID = 123456789
POLL_SECONDS = 10

# None = ещё не запускались: при первом запуске историю пропускаем
last_id = None


def fetch_status():
    """Текущее состояние. None, если сервис недоступен."""
    try:
        return requests.get(f"{BASE}/api/status", timeout=5).json()
    except requests.RequestException as exc:
        logging.warning("backend недоступен: %s", exc)
        return None


def fetch_new_events():
    """Новые события начиная с last_id. Возвращает список и новый курсор."""
    global last_id

    try:
        response = requests.get(
            f"{BASE}/api/events",
            params={"limit": 200, "event_type": "DOWNTIME_FINISHED"},
            timeout=5,
        )
        response.raise_for_status()
        data = response.json()
    except requests.RequestException as exc:
        logging.warning("не удалось прочитать события: %s", exc)
        return [], last_id

    if last_id is None:
        # Первый запуск: пропускаем накопленное, чтобы не засыпать
        # сообщениями за всю историю. Курсор берём из последнего
        # события БЕЗ фильтра: при фильтре total — это число
        # отфильтрованных событий, а не максимальный id.
        probe = requests.get(
            f"{BASE}/api/events", params={"limit": 1}, timeout=5
        ).json()
        items = probe.get("items") or []
        last_id = items[0]["id"] if items else 0
        logging.info("первый запуск: курсор поставлен на %s", last_id)
        return [], last_id

    fresh = []
    # items приходят новыми сверху — обрабатываем от старых к новым
    for event in reversed(data.get("items", [])):
        if event["id"] > last_id:
            fresh.append(event)
            last_id = event["id"]
    return fresh, last_id


def format_downtime(event):
    """Текст сообщения. Сумма берётся ГОТОВАЯ, из estimated_loss."""
    minutes = event["duration_seconds"] / 60
    return (
        "🔴 <b>Простой на линии</b>\n"
        f"Камера №{event['camera_id']}\n"
        f"Время: {event['start_time']} – {event['end_time']}\n"
        f"Длительность: {event['duration_seconds']} сек "
        f"({minutes:.1f} мин)\n"
        f"Ущерб: {event['estimated_loss']:,.2f} ₽".replace(",", " ")
    )


def main():
    while True:
        events, _ = fetch_new_events()
        for event in events:
            try:
                BOT.send_message(
                    CHAT_ID,
                    format_downtime(event),
                    parse_mode=ParseMode.HTML,
                )
            except Exception:
                # Ошибка отправки не должна терять событие:
                # last_id двигаем только после успешной отправки
                logging.exception("не удалось отправить сообщение")
                break

        time.sleep(POLL_SECONDS)


if __name__ == "__main__":
    main()
```

Зависимости: `requests`, `python-telegram-bot`.

## 10. Чего делать нельзя

| Нельзя | Почему |
|---|---|
| Считать ущерб своей формулой | Суммы разойдутся с Dashboard и отчётом |
| Сообщать о простое при `line_status: UNKNOWN` | Данных нет, утверждать о простое нельзя |
| Считать простои по `DOWNTIME_STARTED` | У незакрытого события `duration_seconds` и `estimated_loss` равны нулю |
| Отправлять всё подряд при первом запуске | Пришлёт всю историю разом |
| Разбирать `created_at` как местное время | Это UTC, а `start_time` — местное |
| Планировать по `id` на будущее | `id` выдаётся по мере событий; заглядывать можно только назад |
