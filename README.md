# ПромВизор

Контроль простоя производственной линии по видеопотоку с камеры.

Система наблюдает за линией через камеру, определяет остановку
конвейера и уход рабочего из контролируемой зоны (ROI), фиксирует
простой, считает таймер и условный ущерб, сохраняет событие
и показывает результат на Dashboard.

**Стадия проекта:** MVP / Alpha — готовы видео с конвейером, обнаружение
простоя, экономика, хранение, API и Dashboard. Telegram не начат.
DEMO-роликов пока нет, вместо них работает синтетическая сцена.
Актуальный статус по этапам — в файле [`Handoff Lev.txt`](Handoff%20Lev.txt).

### Возможности интерфейса

* **Мониторинг** — «Линии» (таймлайн простоев за сутки), «Камеры»
  (видеопоток с полосой активности), «Сводная» (KPI и последние события)

  уведомления, хранение данных, светлая и тёмная тема

## Ядро: видео → vision → простой

```python
from app.video import create_source
from app.vision import VisionPipeline
from app.engine import EventEngine

vision = VisionPipeline()
engine = EventEngine(camera_id=1, threshold_seconds=30)

with create_source("demo", scenario="stopped_no_person") as src:
    while (frame := src.get_frame()) is not None:
        result = vision.process(frame)

        for event in engine.update(result):
            print(event.describe())

        print(engine.status(result).to_dict())
```

`engine.status()` возвращает `SystemStatus` — ровно тот объект,
который по контракту уходит в Dashboard и Telegram.

Простой фиксируется, когда **линия стоит И рабочего нет дольше
порога**. Рабочий ушёл, а линия работает — простоя нет. Линия стоит,
но рабочий на месте — вероятно обслуживание, простоя нет.

## Хранение данных

SQLite, путь из `DATABASE_PATH` (по умолчанию `promvizor.db`).
Используется только стандартный `sqlite3` — без ORM.

```python
from app.database import Database, EventRepository

with Database("promvizor.db") as db:
    repo = EventRepository(db)
    repo.ensure_camera(1, "Камера №1")

    repo.save_event(event)                 # событие простоя
    repo.save_status(system_status)        # снимок состояния

    history = repo.recent_events(limit=20)
    stats = repo.statistics()              # итоги за период
    current = repo.latest_status()         # для /api/status
```

Таблицы:

| Таблица | Содержит |
|---|---|
| `cameras` | камеры |
| `downtime_events` | события простоя: начало, конец, длительность, ущерб |
| `status_log` | снимки состояния: линия, рабочий, простой, ущерб |

Время записи хранится в UTC: локальное время процесса может меняться,
а история простоя от этого меняться не должна. В самих событиях
`start_time` и `end_time` остаются в формате «HH:MM».

## Режим камеры и трек человека

В настройках выбирается, откуда система берёт видео:

| Режим | Что видно |
|---|---|
| **Демо — синтетика** | нарисованная сцена: человек ходит, уходит, появляется снова |
| **Демо — ролики** | готовые ролики сценариев из `demo/` (пока их нет) |
| **Веб-камера** | живая камера компьютера, камера выбирается из списка |
| **Сетевая камера** | в Alpha недоступна: в окне будет «нет сигнала» |

В окне камеры видно живое видео с разметкой:

* **зелёная рамка** — рабочий в контролируемой зоне;
* **«Рабочий N»** — номер человека, не меняется от кадра к кадру;
* **линия пути** — где человек был и куда прошёл;
* **красная рамка** — рабочего нет, линия стоит.

Логика простоя: рабочий есть — событий нет; рабочий исчез из кадра —
через **5 секунд** (именно в режиме веб-камеры) простой попадает в
отчёт. Дальше с событием работает Telegram Bot — как читать события,
описано в [`TELEGRAM-GASUN.md`](TELEGRAM-GASUN.md).

### Если видео с веб-камеры чёрное

Чёрный прямоугольник в окне камеры — это не «камера сломалась», а
недостающее объяснение. Дальше видно, какая именно причина.

Что делать, по порядку:

1. **Посмотрите, что написано в окне камеры.** Там причина:
   «Нет сигнала», «Камера отдаёт чёрные кадры» или адрес, по
   которому поток недоступен. Если окно пустое — поток не начался.

2. **Проверьте `/api/video/state`:**

   ```bash
   curl http://127.0.0.1:8000/api/video/state
   ```

   Поле `error` — причина, `source_label` — чем открылась камера
   (например `через V4L2`), `frames` — растёт ли счётчик кадров.
   Если `frames` стоит на нуле, источник не открылся вовсе.

3. **Камера занята другой программой.** Устройство открывается
   только одним процессом: браузер с видео, OBS, Zoom, видеоредактор.
   Закройте их — камера освободится. В списке камер та, которую держит
   конвейер, помечена «сейчас используется конвейером»: это не поломка.

4. **Нет доступа к камере (чёрные кадры при работающем устройстве).**
   В macOS это «Системные настройки → Конфиденциальность и
   безопасность → Камера»: там должен быть разрешён терминал, из
   которого запущен backend. Без разрешения macOS отдаёт чёрные кадры
   без всякой ошибки. В Linux — membership в группе `video`
   (`sudo usermod -aG video $USER`, затем перелогиниться).

5. **Обновите страницу.** Статика отдаётся с версией в адресе, так
   что правки подхватываются сразу; если экран выглядит старым —
   сделайте жёсткое обновление (Ctrl+Shift+R).

Проверить камеру в обход приложения:

```bash
# Linux
ffmpeg -f v4l2 -i /dev/video0 -frames:v 1 out.jpg
# macOS
ffmpeg -f avfoundation -list_devices true -i ""
```


### Вручную

```bash
.venv/bin/python -m app.api.main
```

Открыть: **http://127.0.0.1:8000/** — это Dashboard, он раздаётся тем
же сервером. Документация API: `http://127.0.0.1:8000/docs`

Пока база пуста, на Dashboard нечего показывать. Наполнить
демонстрационными данными (по той же формуле ущерба, что и в рабочем
режиме):

```bash
curl -X POST "localhost:8000/api/demo/seed?days_back=7"
```

Обновить демо-данные с очисткой:

```bash
curl -X POST "localhost:8000/api/demo/seed?days_back=7&replace=true"
```

> Демо — снимок на момент наполнения. Идущий простой «стареет» вместе
> с реальным временем, а снимок статуса остаётся прежним. Со временем
> они расходятся — перезапустите наполнение. В рабочем режиме этого
> расхождения нет: события пишутся непрерывно.

Если backend не отвечает, Dashboard показывает демонстрационные данные
и честно пишет об этом — «Нет связи с сервером». Молча подсовывать
выдумку нельзя: на экране смотрел бы человек, решивший бы, что линия
стоит.

## Развёртывание на сервере

Локальный запуск и серверный отличаются тремя вещами, о которых стоит
знать заранее:

1. **`API_HOST` по умолчанию `127.0.0.1`.** Наружу не достучаться.
   Для сервера нужно `0.0.0.0`.
2. **SQLite-файл `promvizor.db`** — это и есть вся история простоя.
   Его нужно сохранять при переустановке и обновлении: потеря файла =
   потеря данных о простое за все дни.
3. **Один процесс — один конвейер видео.** `app/api/runtime.py` держит
   конвейер в памяти процесса, поэтому `uvicorn` обязан стартовать с
   `--workers 1`. При двух воркерах камера откроется дважды, второму
   потоку она не достанется, а в базу полезут дубли событий.

### Схема

```text
браузер ──https──▶ nginx (443) ──http──▶ uvicorn :8000 ──▶ SQLite
                                                       └──▶ RTSP-камера
Telegram ──▶ бот ──http──▶ uvicorn :8000
```

### Вариант 1 — Docker (рекомендуется)

```bash
cp .env.example .env
# заполнить RTSP_URL, COST_PER_MINUTE, TELEGRAM_BOT_TOKEN

docker compose up -d --build
docker compose logs -f api
curl http://127.0.0.1:8000/api/health
```

Нужен Docker Compose **v2.24 или новее**: в `docker-compose.yml` файл `.env`
объявлен необязательным (`env_file: required: false`), без этого compose
ругается на отсутствующий файл при первом запуске.

Проверить версию: `docker compose version`.

Порядок запуска. Сначала поднимите в режиме `demo` (значение по
умолчанию) и убедитесь, что Dashboard открылся. Только потом задайте
в `.env` `FORCED_CAMERA_MODE=rtsp` и реальный `RTSP_URL` и
перезапустите:

```bash
docker compose up -d
docker compose exec api curl -fsS http://127.0.0.1:8000/api/video/state
```

Поле `error` — причина, почему камера не открылась; `frames` растёт ли.

| Что | Файл |
|---|---|
| Образ backend | `Dockerfile` |
| Образ бота | `Dockerfile.telegram` |
| Оркестрация, тома, сеть | `docker-compose.yml` |
| Что не копировать в образ | `.dockerignore` |
| Зависимости без YOLO | `requirements-lite.txt` |

Образ по умолчанию **без `ultralytics`** (~450 МБ): хватает для
видеопотока, API, Dashboard и всех тестов. С детекцией человека:

```bash
docker compose build --build-arg INSTALL_YOLO=1
```

образ станет ~2.5 ГБ, и VPS с 2 ГБ RAM не потянет — тогда берите
машину побольше или оставайтесь на demo.

### Вариант 2 — без Docker, systemd

```bash
sudo bash deploy/install.sh
sudo nano /opt/promvizor/.env      # проверить перед запуском
sudo systemctl start promvizor-api
sudo journalctl -u promvizor-api -f
```

Скрипт ставит ffmpeg, создаёт пользователя `promvizor` без прав root,
собирает venv, кладёт юниты и включает автозапуск. Сертификат не
выпускает — для этого нужен домен, который вы уже купили и направили
на IP сервера (Let's Encrypt не выпускает сертификаты на голый IP).

```bash
# переустановить зависимости с YOLO
sudo -u promvizor /opt/promvizor/.venv/bin/pip install \
  -r /opt/promvizor/requirements.txt
sudo systemctl restart promvizor-api
```

> `install.sh` сам дописывает в `.env` `YOLO_CONFIG_DIR` — каталог
> весов внутри `data/`. Это обязательно: юнит работает с
> `ProtectHome=true`, то есть `/home/promvizor` недоступен, и без
> этого пути первая попытка скачать модель упала бы с ошибкой записи.
> Если `.env` вы правили руками — проверьте, что строка на месте.

Юниты: `deploy/systemd/promvizor-api.service`,
`deploy/systemd/promvizor-telegram.service`.

### nginx и HTTPS

```bash
sudo cp deploy/nginx/promvizor.conf /etc/nginx/sites-available/promvizor
sudo ln -s /etc/nginx/sites-available/promvizor /etc/nginx/sites-enabled/
# в файле заменить promvizor.example.ru на свой домен
sudo certbot --nginx -d ваш-домен
sudo nginx -t && sudo systemctl reload nginx
```

Порт 8000 намеренно слушает только `127.0.0.1`: наружу смотрит nginx с
сертификатом. Иначе приложение было бы доступно и по http, в обход
сертификата.

Отдельный `location /api/video/` в конфиге — не украшение. Буферизация
nginx накапливает кадры и отдаёт их пачкой, картинка в окне камеры
дёргалась бы и отставала; а multipart-поток без `Content-Length` nginx
считает бесконечным и обрывает стандартным таймаутом в 60 секунд.

`/docs` и `/openapi.json` в конфиге закрыты (`deny all`) — на публичном
сервере карта API не нужна.

### Что учесть на VPS

* **Камера должна быть достижима с сервера.** Внутренний RTSP-адрес
  вида `192.168.x.x` из интернета недоступен. Варианты: сервер внутри
  сети завода (проще всего), WireGuard-туннель или открыть RTSP наружу
  (плохо — это видео с цеха без авторизации).
* **Веб-камера в контейнере не заработает** — у контейнера нет доступа
  к USB. Внутри контейнера остаются `demo` и `rtsp`.
* **ffmpeg обязателен в образе.** OpenCV открывает RTSP через `CAP_FFMPEG`;
  без ffmpeg камера отдаёт пустой поток, и в логах при этом ничего
  подозрительного нет.
* **Не ставьте `FORCED_CAMERA_MODE` бездумно.** Он перекрывает выбор в
  интерфейсе намертво. Для стенда оставьте пустым, для боевого сервера
  задайте `rtsp`.
* **Токен Telegram** — только в `.env` на сервере. В `docker-compose.yml`
  и в git он не попадает.
* **Защиты приложения нет.** Ни авторизации, ни HTTPS внутри. На публичном
  сервере закрывайте доступ к API на уровне nginx (базовая аутентификация
  или VPN) — иначе `/api/demo/seed` и переключение режима камеры доступны
  любому, кто открыл адрес.

## API

Запуск сервера:

```bash
.venv/bin/python -m app.api.main
```

Документация с примерами запросов и ответов: `http://127.0.0.1:8000/docs`

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/status` | текущее состояние системы |
| GET | `/api/status/history` | снимки состояния, свежие сверху |
| GET | `/api/events` | история простоя, фильтры и пагинация |
| GET | `/api/events/{id}` | одно событие, 404 если нет |
| GET | `/api/statistics` | итоги за период |
| GET | `/api/statistics/by-camera` | итоги по камерам |
| GET | `/api/cameras` | зарегистрированные камеры |
| GET | `/api/config` | стоимость минуты и настройки |
| GET | `/api/health` | живость сервиса и базы |
| POST | `/api/demo/seed` | наполнить базу демо-данными |

Примеры:

```bash
curl localhost:8000/api/status
curl "localhost:8000/api/events?limit=20&event_type=DOWNTIME_FINISHED"
curl "localhost:8000/api/statistics?since=2026-10-01&until=2026-10-10"

# демо-данные, чтобы было что показать до подключения видео
curl -X POST "localhost:8000/api/demo/seed?days_back=7"
```

Особенности:

* **Ущерб не пересчитывается в API** — приходит из базы готовым.
* **Пустая база — не ошибка:** `/api/status` отдаёт `UNKNOWN` с нулями.
* **API только читает.** Запись идёт из процесса обработки видео
  прямо в базу, так API нельзя испортить внешним запросом.
* **Демо-данные — только по явному запросу** и по той же формуле
  `calculate_loss()`. Молча наполнять базу нельзя: интерфейс показал бы
  цифры, которых на заводе нет.

## Расчёт ущерба

```text
loss = downtime_minutes × cost_per_minute
```

Пример: `100 мин × 750 ₽ = 75 000 ₽`

Формула реализована **один раз** в `app/core/types.py` → `calculate_loss()`.
Считает backend (Lev). Dashboard и Telegram только отображают
готовое значение и не пересчитывают его самостоятельно —
это требование раздела 14 Handoff.

## Детекция человека: зона, модель, скорость

Разобран 14.10.2026. Здесь зафиксировано то, что иначе придётся
выяснять заново, — особенно на другой машине.

### Главная причина «человека не видно» была не в зоне

В `app/vision/person_detector.py` размер входа был **зашит в код:
`imgsz=416`**. На далёком плане цеха рабочий занимает ~40 пикселей
по высоте — в 416 он превращался в пятно в несколько пикселей,
мимо которого YOLO проходил.

Это обнаружилось только после замера: расширение зоны само по себе
почти ничего не меняло (ролик «человек в кадре»: 11/37 → 11/37).

### Замеры

Доля кадров, где найден рабочий, на роликах из `demo/videos/`.
Машина замера: 2 ядра Intel i3-2365M (2012), без GPU.

| Модель | imgsz | ролик «человек в кадре» | мс/кадр | fps |
|---|---|---|---|---|
| yolov8n | 416 | ~5% | ~900 | 1.1 |
| yolov8n | 640 | 23% | 1720 | 0.6 |
| yolo26n | 640 | 31% | 1461 | 0.7 |
| **yolo26n** | **960** | **62%** | **2138** | **0.5** |
| yolo26s | 960 | 92% | 5106 | 0.2 |

Вывод: **размер входа влияет сильнее выбора модели.** yolo26
подтвердилась как выбор — она быстрее v8n и находит заметно больше.
По умолчанию стоит `yolo26n` @ 960.

### Контролируемая зона

Рабочие стоят в **верхней половине** кадра (`y≈0.19–0.62`), а зона
начиналась с `y=0.35` и проходила под ними — человека было видно, но
«в зоне» он не был, и присутствие не определялось.

| | было | стало |
|---|---|---|
| `ROI_LEFT` | 0.20 | 0.15 |
| `ROI_TOP` | 0.35 | **0.12** |
| `ROI_RIGHT` | 0.80 | 0.90 |
| `ROI_BOTTOM` | 0.90 | 0.80 |

Координаты вынесены в `.env`: зона — свойство конкретной камеры,
и под свой план цеха её нужно поправлять без правки исходников.

### ⚠️ Открытые вопросы (продолжить на другом ПК)

1. **Скорость упирается в железо.** Сейчас конвейер даёт ~1.2 fps.
   Смена модели это не лечит — она его усугубляет. Предлагаемое
   решение: детектировать человека **раз в 3–5 кадров**, между ними
   брать последний результат. Детектор движения дёшев и идёт каждый
   кадр — простои он и так поймает. Возврат скорости почти без потери
   точности. **Не сделано, ждёт решения.**

2. **Ролик 4 не соответствует описанию.** Он описан как «конвейер
   останавливается и рабочий тоже уходит», но рабочий в нём почти
   весь ролик (кадры 60–300, уверенность 0.84–0.91). YOLO не
   выдумывает — там действительно человек в каске. Ролик 3 описанию
   соответствует: человек есть до кадра 240, дальше исчезает.
   **Нужен корректный ролик 4.**

3. **Демо-сценарии не дают простоя.** В сценарии 4 статус линии
   остаётся `WORKING`. Логика движка ставит `STOPPED` только для
   режимов `webcam` и `synthetic` — демо в список не входит, а по
   движению в неподвижном ролике ничего не определяется. Чтобы
   демо прогоняло заявленные состояния, это надо доделать.

4. **Разрешение роликов низкое** — 800×368. Перезалив в 1080p, получим
   больше, чем любой сменой модели: YOLO ограничен реальными пикселями,
   а не размером входа.

5. **Статус `UNKNOWN` на веб-камере в спокойной сцене.** При движении
   между порогами (0.008–0.018) статус остаётся неопределённым.
   Расширение зоны детектор движения не сломало — проверено.

## Камера из браузера: считает сервер

Режим **«Веб-камера — из браузера»** нужен там, где камера не у сервера,
а у человека: ноутбук в аудитории, планшет в цеху. Сервер при этом
остаётся единственным местом, где считают: кадры уходят из браузера
на сервер, а YOLO, ROI, детектор движения, простой, таймер и ущерб
считаются только на сервере. В браузере нет ни одной формулы.

Как это работает:

```text
камера ноутбука
   ↓  getUserMedia
canvas → JPEG 4 раза в секунду
   ↓  POST /api/video/browser/frame
сервер: декодирование → YOLO → ROI → движение → простой → ущерб → БД
   ↓
Dashboard + Telegram
```

| Что | Где |
|---|---|
| приём кадра | `app/video/browsercam.py` |
| маршруты | `POST /api/video/browser/frame`, `/stop`, `GET /browser` — `app/api/stream.py` |
| источник для конвейера | `BrowserSource` (тот же интерфейс `get_frame()`) |
| отправка кадров из браузера | `web/js/browsercam.js` |
| режим в настройках | `Настройки → Режим камеры → Веб-камера (из браузера)` |

Ограничения, о которых стоит знать заранее:

* **Нужен HTTPS.** Браузер не отдаёт камеру странице, открытой по
  http (кроме `localhost`). Поэтому сервер за сертификатом — не
  формальность, а условие работы режима. Обходной путь для показа:
  SSH-туннель, тогда адрес будет `127.0.0.1`.
* **Доступ спрашивает браузер, а не сервер.** Отказать в камере
  может только пользователь; из сервера камеру не включить.
* **Кадр считается свежим 0,7 секунды.** Пока браузер шлёт кадры, всё
  работает; как только поток прервался, система честно пишет «нет
  сигнала с браузера» и ждёт возвращения, не закрывая источник.
* nginx для этого режима отдаёт отдельный `location` с
  `client_max_body_size 8m`: общий лимит 1 МБ кадр с телефона не
  пропустил бы.

### Развёртывание на FirstVDS, что оказалось важно

* `docker` на сервере не было, поэтому вариант systemd: `ffmpeg`,
  `python3-venv`, пользователь `promvizor`, юнит
  `promvizor-api.service`, рабочий каталог `data/`.
* **torch ставится CPU-версией**:
  `pip install torch torchvision --index-url https://download.pytorch.org/whl/cpu`.
  Обычная установка тянет CUDA-библиотеки и лишние ~2 ГБ.
* **`ProtectHome=true` закрывает `/home/promvizor`**, поэтому
  `YOLO_CONFIG_DIR` обязан указывать на каталог данных — иначе первая
  загрузка весов упадёт с ошибкой записи.
* **Бесплатные поддомены `*.fvds.ru` делят лимит Let's Encrypt**
  (50 сертификатов на `fvds.ru` в неделю). Когда лимит выбран,
  `deploy/issue-cert.sh` (cron, каждые 10 минут) выпускает сертификат
  сам, как только лимит снят; до этого nginx работает на http.
* **nginx в Ubuntu 24 — версии 1.24**, где директивы `http2 on;` ещё
  нет: параметр переносится в `listen 443 ssl http2;`.
* **Обновление с GitHub**: `promvizor-update` на сервере делает
  `git fetch` + `reset --hard origin/main` + перезапуск сервиса, перед
  этим кладёт бэкап в `/opt/promvizor-backup-*.tar.gz`. Секреты и
  база (`.env`, `data/`) под версией не лежат и при обновлении не
  страдают.
* **Telegram с сервера может быть недоступен** (таймаут до
  `api.telegram.org` у части хостингов). Бот при этом продолжает
  читать backend и формировать сообщения — падает только отправка.

### Вход на сайт по паролю

На сервере сайт закрыт паролем:

```bash
AUTH_ENABLED=1
AUTH_LOGIN=akylov
AUTH_PASSWORD_HASH=<sha256 от пароля>
```

Хеш считается один раз:

```bash
python -c "import hashlib;print(hashlib.sha256(b'пароль').hexdigest())"
```

Как спрашивается пароль:

| Действие | Спрашивает? |
|---|---|
| открыли новую вкладку | **да** |
| обновили страницу (F5) | нет |
| закрыли и снова открыли вкладку | **да** |

Технически отметка о входе лежит в `sessionStorage` — единственное
браузерное хранилище, отдельное у каждой вкладки. Сервер сверяет её
на каждом запросе (`app/core/auth.py`).

Почему не HTTP Basic на nginx: браузер запоминает такие учётные данные
на всю сессию, и после первого входа пароль не спросили бы нигде.

Что и чем защищено:

* **закрыты данные** — без пароля любой запрос к `/api/*` получает
  401, включая видеопоток и статистику;
* **открыты страница и её файлы** (`/`, `/js/*`, `/css/*`) — иначе
  после входа перезагрузка снова получила бы форму входа: браузер не
  умеет вешать свои заголовки на навигацию.

Пароль нигде не хранится: в `.env` только SHA-256, в коде и в браузере
его нет, на странице входа он не напечатан.

### Telegram через прокси

Если до `api.telegram.org` с сервера не достучаться:

```bash
TELEGRAM_PROXY_URL=http://пользователь:пароль@хост:порт
TELEGRAM_PROXY_ENABLED=1
```

Прокси используется **только** для связи с Telegram. Обращения к API
ПромВизора идут напрямую: пускать данные о простое завода через
сторонний прокси незачем.

`TELEGRAM_CHAT_ID` принимает несколько чатов через запятую —
уведомление уйдёт каждому:

```bash
TELEGRAM_CHAT_ID=111111,222222
```
